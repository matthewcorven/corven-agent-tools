# Fictional input: release-note review

This teaching fixture is not a real user's approved PRD. Nothing is implemented.

R1. A release owner wants a concise, accurate release-note draft from a selected change list.
Every statement must link back to a source item. The owner reviews the draft; publication is separate.

R2. The reference ambition includes scheduling, multiple repositories, automatic publishing,
localization and a general drafting assistant. Reconsider which breadth earns its cost first.

R3. No external publication in the proposed pilot. Source retrieval is read-only. Source references
and a run record must be available with a successful draft. Missing evidence blocks completion.
Draft retention, access and source-content policy are undecided and must be settled before real data.

R4. The owner can request, inspect and cancel a run. Cancellation prevents new steps; admitted work
must reach a known result or an explicitly unknown state. A timeout is not proof that no work occurred.
Restart requires inspecting the run record rather than claiming success or blindly repeating work.

R5. One implementation lead owns scope, one builder prepares a candidate, one reviewer evaluates
evidence, and the owner decides activation. These are illustrative responsibilities, not configured agents.

R6. Template changes apply between runs. A candidate is validated and reviewed against an exact
version. A stale approval cannot activate a different candidate. Urgent restrictions apply immediately;
they do not wait for a convenient version switch.

R7. Limits, accepted source identities, data access, retention and acceptance fixtures remain open.
The proposal must identify them rather than invent numbers or imply approval.
